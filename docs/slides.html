Acme Finance · vulnerability governance

Org-wide vulnerability governance

セキュリティスキャンを、 各リポジトリに任せない。

同じ Organization の中に特別なプロジェクトを 1 つ置くだけ。 それがコントロールプレーンになり、配下をまとめて検査・報告し、必要なら修正 PR まで担う。

Before

よくあるやり方の弱み

  • スキャンを各プロジェクトの CIに埋め込む
  • チームごとに導入がずれ、やり忘れが起きる
  • 新規リポジトリは「誰かが workflow を足すまで」見えない
  • Org 全体の状態を一目で見る場所がない

Contrast

埋め込み CI と、中央統制

分散 · 各リポジトリ CI

任意参加

workflow を置いたリポジトリだけが対象。置かない／壊れたままのリポジトリはサイレントに漏れる。

集中 · コントロールプレーン

強制カバレッジ

Org 配下を毎回列挙して検査する。アプリ側にスキャナをコピーしない。増えたリポジトリも次の run から自動で入る。

Point

今回の方式のポイント

  • セキュリティスキャンは各プロジェクトの CI には組まない
  • Org 内の特定 1 プロジェクトから全体をスキャンする
  • だから強制力があり、やり忘れがない
  • 横断レポートは勝手に作られる（Issue + Pages）
  • ポリシーを通った CRITICAL は、修正 PR も自動で開ける

金色の 1 枠だけがスキャン側 ほかの四角はアプリ。スキャナのコピーは不要

発見 · Trivy · ポリシー · Cloud Agent · Issue / Pages は、すべてこの 1 プロジェクトに集約する。

Sequence · GitHub Actions

governance-demo の Actions が ほかのプロジェクトを検査する流れ

スキャナもポリシーも Actions の置き場所は governance-demo だけ。アプリ側の CI には載せない。

Enforcement

登録ゼロ

やり忘れが構造的に起きない

  • 対象はリスト登録ではなく、Org の持ち物を毎回数え直す
  • 外す唯一の出口は exemptions（理由と見直し日つき）
  • リポジトリが増えても、アプリチームが workflow を足す必要はない

Nightly flow

修正（任意）Cursor Agent

レポート
  • 発見は Organization Token で動く。全リポジトリ（新規含む）を毎晩自動で列挙する
  • 検査は Cursor 枠を使わないので、全リポジトリ並列で回せる
  • Agent は「直すとき」だけ。トークンは直す回数に比例

Reporting

レポートは勝手にできる

  • Issue — 「今夜どうだったか」の横断サマリ（毎回起票）
  • GitHub Pages — 「今どれだけ開いているか」の断面を毎 run で焼き直す
  • ダッシュボード常駐は不要。artifact → snapshot → 静的 HTML

例: acme-finance-demo.github.io/cursor-governance-demo

Remediation

場合によっては PR も作る

  • 自動修正はポリシーがコードで決める（エージェントの裁量ではない）
  • 既定は CRITICAL かつマイナー／パッチ上げのみ。メジャー上げは人手
  • 1 パッケージグループ = 1 PR。予算と二重提出防止つき
  • スキャンだけ／修正あり、は手動実行のフラグで切り替え可能

Takeaway

覚えること、3 つ

  • 1. 同じ Org に特別なプロジェクトを 1 つ置く（各 CI ではない）
  • 2. 列挙ベースなので強制され、やり忘れない
  • 3. レポートは自動。修正 PR はポリシーが通ったときだけ

シフトレフトが欲しければ、同じコントロールプレーンを reusable workflow で呼ぶ道もある — コピーはしない。
